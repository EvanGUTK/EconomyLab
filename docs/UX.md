# EconomyLab — experience and visual direction

## Design thesis

Make progression a journey, not a single average. A designer should see where agents wait, who never arrives, and which resource condition changes after a balance edit.

## Screen model

| Screen / surface | Primary task | Interaction and state |
| --- | --- | --- |
| Economy editor | Inspect prerequisites and costs | Graph selection opens units and source/sink definitions |
| Cohort setup | Choose behavior assumptions | Show policy and session differences before running |
| Progression report | Find bottlenecks | Completion curves and waiting-reason drilldown |
| Balance comparison | Review one proposed change | Paired distributions with unreached fractions |
| Run replay | Explain one trajectory | Event timeline and resource ledger stay synchronized |

## Visual system

The repository identity uses ink backgrounds, rose scenario accents, distinct cohort line patterns, and progression maps with labeled gates. The application should develop this direction with readable typography and deliberate information hierarchy. Numbers align by scale and unit. Visual emphasis belongs to the active question, selected event, unresolved discrepancy, or next action. Avoid filling the opening view with interchangeable statistic cards.

## Interaction rules

Selection persists when the user changes a filter, or the UI explains why the selected object is now outside the view. Comparisons preserve each run's identity and configuration. Loading, empty, incomplete, invalid, stale, and successful states are distinct. A result panel keeps the evidence drawer available so the user can inspect source events without losing context.

Keyboard navigation covers the primary journey. Color is reinforced by text, symbols, or line patterns. Tooltips expand unfamiliar terms but do not hide required units or failure reasons. Text and chart axes remain readable at normal laptop sizes. Destructive local edits provide a review of their exact scope and preserve recoverable prior revisions where feasible.

## First demonstration storyboard

Compare a baseline with one upgrade price change using identical declared scenarios. Highlight an agent who never reaches the third upgrade, inspect its waiting reason, and show how a revised configuration changes both completion rate and resource flow.

The first demo uses synthetic or explicitly redistributable material and carries an illustrative label until the runtime produces it. The committed SVG banner is an identity asset, not evidence of a working application. Future screenshots should come from the application at a recorded revision.
